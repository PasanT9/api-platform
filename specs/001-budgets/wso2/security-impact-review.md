| **Authorization & Access Control** (*Complete if introducing or modifying REST APIs)* |  |
| **Authentication**: Is authentication required for all exposed API endpoints? | Yes, by design. **Public** `/api/v0.9/budgets` and `/api/v0.9/budgets/{budgetId}` are declared under the existing `OAuth2Security` scheme in `platform-api/resources/openapi.yaml` and pass through the existing platform-api token middleware. **Internal** `GET /api/internal/v1/budgets` (gateway resync) uses the existing gateway-token authentication (`authenticateRequest` in `platform-api/internal/handler/gateway_internal.go`); the path is added to `SkipPaths` only to bypass the user-token middleware, not authentication. **Websocket** `budget.created|updated|deleted` messages travel platform-api → gateway-controller on the existing authenticated gateway websocket. No new controller endpoint and no inbound usage interface exist (the usage-ingest endpoint of the earlier design was removed on 2026-10-09). Gateway callers: no new authentication; budgets use the identity already established by the route's authentication (FR-012). |
| **Authentication Mechanism:** How is authentication enforced?  | Public API: OAuth2 bearer JWT validated by the existing platform-api middleware, with the organization taken from the verified token. Internal resync: gateway token (`authenticateRequest`). Websocket: the existing gateway-authenticated connection. Shared Redis: username/password (ACL) and TLS including mutual TLS, using the same settings shape as the advanced rate-limit Redis client (FR-022b). |
| **Privilege Level Defined:** What privilege level is required for the endpoints? (Admin, Publisher, Subscriber, Internal/System, Anonymous) | **Admin** for create / update / delete: new scope `ap:budget:manage`, mapped by default to `ap_admin` in `platform-api/resources/role-to-scope-mapping.yaml`. **Read** (list, get): `ap:budget:read`, mapped to `ap_operator`; holders of `ap:budget:manage` can also read. Whether `ap_viewer` also gets `ap:budget:read` is NOT ANSWERED (open product decision; proposed: no). **Internal/System** for the gateway resync endpoint and the websocket messages. No anonymous access. Overrides (most specific wins, 2026-10-14): a more specific budget can lift a broader one for one value — including a Monitor budget over an Enforce budget — so creating one needs the same `ap:budget:manage` scope, returns a `BUDGET_OVERRIDES_OTHER` warning naming the affected budgets, and is audit-logged with before/after values. |
| **Least Privilege Enforcement:** Is access restricted to the minimum required privilege? (Lower-privileged roles must NOT gain unintended access.) | Yes, by design. Each operation declares its scope: reads accept `ap:budget:read` or `ap:budget:manage`; writes accept only `ap:budget:manage`. Other roles do not see or change budgets unless granted (FR-027). Being a member of a budget's owner (a project's members, a team) grants nothing (FR-028). Per-project delegation is not offered. In the AI Workspace, Create / Edit / Disable / Delete are hidden for `ap:budget:read` holders, and the API enforces the same rule independently. Read-only mode is enforced in the budget service and repository layers, not only in handlers (GO-AUTH-015). Confirming that the handler-level scope check follows deny-by-default (GO-AUTH-007) is NOT ANSWERED until the code exists. |
| **Resource Ownership Check (BOLA / IDOR):** When accessing a resource using an ID in the URL, does the system verify that the authenticated user has permission to access that specific resource? *(Example: Preventing User A from accessing another user’s order via `/api/orders/{orderId}`)* | Yes, by design. `budgetId` (the budget handle, unique per organization) is always looked up together with the organization from the verified token. A budget of another organization returns 404 `BUDGET_NOT_FOUND`, identical to a nonexistent budget. `context.project` and every owner `value` (project / LLM provider / LLM proxy / application handle) are resolved only within the caller's organization (and, for a project context, proxies and applications only within that project); a reference to another organization returns 404 `BUDGET_OWNER_NOT_FOUND`, identical to a nonexistent resource. Budgets are organization-wide resources with no per-user ownership; project-mode budgets are listed per project but need the same organization-level scopes in v1. On the gateway path, a refusal or header for a budget with "each" owners names only the caller's own values. |
| Is case sensitivity consistently enforced for user identities and role checks during authorization and other validations? | NOT ANSWERED. Whether claim names and claim values (for example `sub` email addresses) are matched case-sensitively when a request is mapped to a claim budget is not specified. If matching is case-sensitive and the identity provider varies case, the same user could receive more than one allowance. Scope checks use the existing platform-api scope matching, unchanged. |
| **Cross-Tenant Isolation:** Does the feature strictly enforce tenant boundaries? (e.g., preventing Tenant A from accessing Tenant B resources) | Yes, by design. Every `budgets` row is keyed to an organization. The organization always comes from verified context (the JWT for the public API; the gateway token or websocket connection internally), never from a payload, path or query (GO-AUTH-005). Budget definition events are broadcast only to the gateways of the owning organization; the controller is bound to one organization and never takes it from the payload. The resync endpoint returns only the gateway's organization's budgets. Redis keys are per budget uuid (globally unique), so organizations sharing one Redis never share counters. Cross-organization lookups return the same 404 as a missing resource. |
| **Mass Assignment Protection:** Are strict DTOs / whitelists used to prevent users from submitting unintended fields (e.g., `is_admin: true`)? | Yes, by design. Create and update requests are decoded strictly against `CreateBudgetRequest` / `UpdateBudgetRequest`; unknown fields are rejected with 400 `BUDGET_INVALID`. Organization, `statusReason`, `amount_version` and audit fields cannot be set by the client. An attempt to change scope type, shared vs separate, owner or period is rejected with 400 `BUDGET_IMMUTABLE_FIELD`. |
| **User Input & Web Protection** |  |
| **Output Encoding (XSS Prevention):** If user-provided data is rendered in the UI (stored or reflected), is it contextually encoded to prevent XSS? | Yes, as a design requirement for the AI Workspace (React 19 + MUI). Values rendered are the budget display name, description, claim names, the claim value of a specific-value claim owner, owner display names and the "created by" user. All must be rendered with React's default JSX text interpolation, never `dangerouslySetInnerHTML`; values placed in link URLs (the Moesif deep-link Budget filter) must be encoded with `encodeURIComponent` (`.claude/rules/js-output-encoding-xss.md`). On input, claim names are restricted to `^[A-Za-z0-9_.:-]{1,255}$`; display name (≤ 255) and description (≤ 1,023) have length limits only. The AI Workspace no longer shows per-value claim values taken from callers' tokens. Those values appear in the embedded Moesif analytics (Budget Usage card rows, alert messages). How Moesif renders event metadata is outside this product; NOT ANSWERED whether it encodes them. The gateway 429 body is JSON and includes the budget display name. |
| **SSRF Prevention:** If the server fetches user-provided URLs, are they validated against a strict allow-list? | N/A. The feature fetches no user-provided URL. The gateway connects only to the operator-configured Redis; platform-api publishes nothing to Moesif; the AI Workspace analytics links use the operator-set `APIP_AIW_MOESIF_ANALYTICS_URL`. |
| **XXE Prevention:** If parsing XML, are DTDs and external entities explicitly disabled using secure XML parser configurations? | N/A. No XML is parsed. All new payloads are JSON (REST, websocket) or TOML configuration. |

There are no sort parameters. Mapping each accepted value to a hardcoded column or fragment, rather than interpolating it, is NOT ANSWERED until the code exists. |

DDL (including the guarded `ALTER TABLE audit ADD … details`) uses the existing mechanism of re-applying idempotent schema files at startup, so no new class of database privilege is introduced. Whether the startup `ALTER` on a shipped table needs a privilege some deployments withhold is NOT ANSWERED. |

| **Secure Coding & Operational Safety**  *(Mandatory for all implementations.)* |  |
| **Sensitive Data in Logs:** Any passwords, API keys, tokens, or PII logged?  If logging is mandatory, is proper masking applied? | No claim values, API keys, tokens or Redis passwords are logged at INFO and above (design rule). The gateway logs a refusal at DEBUG with budget id, scope type and period label only; Redis failures log the Redis endpoint, not credentials. Metrics use low-cardinality labels only (no user, claim or budget values). platform-api logs create / update / delete with budget id and actor; the actor is a user identifier, also written to the audit log. **PII notes**: (1) per-value claim values are hashed (SHA-256, first 32 hex characters) in Redis key names, so no raw emails are stored in Redis. (2) Each AI request event sends the caller's own claim value to Moesif as `budget_owner_values`, where it appears on the Budget Usage card rows and in alert messages for everyone who can open the organization's analytics. Whether this needs masking or a narrower audience is NOT ANSWERED. |
| **In-Memory Sensitive Data Handling (Heap Inspection Protection)** Are sensitive data (e.g., passwords, encryption keys, tokens) stored using mutable data types (e.g., `char[]`) instead of immutable types like `String`, and explicitly cleared from memory immediately after use to prevent heap inspection attacks? | N/A. The services are Go. The only new secrets are the Redis password and TLS client key, held by the go-redis client in the same way as the existing rate-limit Redis client. |
| **Response and error Handling:** Are client responses generic, and server information or stack traces remain internal? | Yes, by design. `/budgets` errors use the standard `{status, code, message}` body with generic messages (owner values are never echoed); the specific field and reason are logged at DEBUG only. Unexpected errors return 500 with a generic message and a random tracking id; the stack is logged at ERROR. Cross-organization lookups return the same 404 as a missing resource. Redis unreachable returns 503 `BUDGET_CHECK_UNAVAILABLE` with a generic message and no Redis detail. Client-facing headers are platform-neutral (`Budget-Id`, `Budget-Remaining`, `Budget-Reset`, `Budget-Monitor`) per `.claude/rules/error-handling.md` directive 2. **Intentional disclosure to callers**: a 429 `BUDGET_EXHAUSTED` body names the refusing budget (id, display name, context and owners including the caller's own claim values for "each" owners, period, amount, reset time), and allowed responses carry the most constraining budget's id, remaining amount and reset time (FR-013, FR-014), so API consumers can see budget names and amounts that apply to them. The 401 body shape for the new endpoints follows platform-api's shared response; alignment with the repository rule's prescribed body is NOT ANSWERED (platform-wide). |
| **Secrets Management:** No hardcoded credentials. Stored in Secret Manager / Vault / Env. | Yes. No credentials are hardcoded in code. The Redis password and TLS material come from environment variables or file references (Kubernetes Secret via `existingSecret` in Helm), never inline in a ConfigMap. Existing gateway and controller credentials are reused unchanged. |
