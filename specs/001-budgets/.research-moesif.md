# Research: Moesif as the budget-warning delivery channel

Date: 2026-10-08. Sources: public Moesif / WSO2 docs and blogs (web research only; no in-product verification). Items marked **UNVERIFIED** were not found in public docs and need confirmation with the Moesif team or in a trial account.

## 1. Alerting

- **Alert types**: static thresholds (operators `>`, `<`, `>=`, `<=`, `any`) and dynamic alerts (anomaly detection; Increase/Decrease/Both; needs "a couple days" of history).
  https://moesif.com/docs/api-monitoring/creating-alert-rules ,
  https://moesif.com/docs/guides/guide-for-setting-up-static-alerts-for-apis ,
  https://moesif.com/docs/guides/guide-for-setting-up-dynamic-alerts-for-apis ,
  https://www.moesif.com/docs/api-monitoring/
- **Alert rules are built from a time-series chart**: every chart filter becomes an alert filter, and a chart **group by** makes the alert *multi-dimensional*, so Moesif "monitors each of the group by values separately" ("a single alert rule that monitors hundreds of different metrics"). The webhook payload has `grouping_feature_level1/2`, which suggests at most **2 group-by levels** (inferred from the payload, not stated in the docs).
- **Metadata fields**: Moesif says "any metadata fields you set can be used to create billable metrics … quotas, reports, alerts, and more." https://www.moesif.com/docs/ingest-action-events/collector-api/ . Chart metrics include sum/avg/min/max/percentile/distinct on numeric fields, with `metadata.revenue` given as an example (see §2). So filtering on `metadata.budget.id` (or similar), grouping by it, and alerting on `sum(metadata.llm_cost)` should all be supported. **UNVERIFIED**: whether a deeply nested metadata path such as `metadata.budgets[].id` (an array) can be filtered or grouped. Arrays of objects are unlikely to group cleanly, so use flat scalar keys.
- **Evaluation windows (main limitation)**:
  - *Real-time rolling* (minutes to hours): evaluated **every minute** over overlapping windows (12:00–12:15, 12:01–12:16, …). https://www.moesif.com/docs/api-monitoring/real-time-alerts
  - *Calendar-based* (daily, weekly, **monthly**): evaluated **once, after the calendar period ends** (e.g. after midnight for daily). The docs say these are "not real-time" and "retrospective". Time zone is set per app. https://www.moesif.com/docs/api-monitoring/calendar-based-alerts/
  - So a rule like "sum(metadata.llm_cost) by team over the calendar month ≥ 80% of budget" **will not fire mid-month**. Moesif checks it only after the month closes. A rolling window covers hours, not a month-to-date. Moesif alerts can't natively compute month-to-date spend against a budget mid-period.
- **Thresholds are static numbers per rule**. A multi-dimensional rule applies one threshold to every group. There is no documented way to compare against a per-group budget amount, i.e. a threshold read from another field (**UNVERIFIED**, likely not possible). Per-budget amounts would need one rule per budget, or a percent field computed by the gateway.
- **Channels**: Email (includes a time-series chart), SMS, Slack (incoming webhook), PagerDuty, Webhook (JSON: `type`, `name`, `metric`, `grouping_feature_level1/2`, `metric_values[{feature,value,direction}]`, `timestamp`, `history`; HTTPS plus secret recommended). Each alert rule and each channel has its own **throttle** (e.g. 1 notification per hour), and a rule silences repeat alerts after the first notification. Rules also support silencing and downtime windows. https://moesif.com/docs/api-monitoring/creating-notification-channels
- **Customer-facing warnings**: Behavioral Emails send emails to members of a cohort (e.g. customers nearing a quota), and workflows can be triggered from an alert rule or a cohort. Cohort refresh frequency is **UNVERIFIED**. https://www.moesif.com/blog/developer-marketing/behavioral-emails/Automatic-Notification-of-Quota-and-Billing-Issues/ , https://www.moesif.com/docs/user-analytics/saved-cohorts
- **Per-plan limits on alert-rule count**: not published (**UNVERIFIED**). The pricing page lists only event volumes, $75 per extra seat on self-serve, and 1-year retention on paid plans. https://moesif.com/price

## 2. Dashboards (budget vs actual)

- Segmentation and time-series charts support **sum/avg/min/max/accumulate/percentile/distinct** on numeric fields, including metadata (example: `metadata.revenue`), with multiple group-bys and custom formulas (+ − × ÷, ^, sqrt, log). https://moesif.com/docs/api-analytics/segmentation
- Calendar-aligned intervals exist ("last 1 month" starts at 12 AM on the 1st). https://www.moesif.com/docs/api-analytics/date-math/
- So a chart of `sum(metadata.llm_cost)` grouped by `metadata.budget_id` with monthly buckets is feasible. The **"accumulate"** metric gives a running month-to-date line. A *budget* line needs either a constant formula per chart or the budget amount sent on each event, e.g. `max(metadata.budget_amount)` per group (feasible, but not a documented pattern).

## 3. Governance, quota rules and billing meters

- Governance rules: *behavior/cohort* rules and *quota* rules ("block after 10,000 API calls in the current billing month"). They can block requests or modify the response, e.g. add headers. They are enforced through the Moesif server integration and are **incompatible with the Tyk and Azure APIM integrations**. Rules **block or modify; they do not notify**. Evaluation and sync latency is not published (**UNVERIFIED**; cohort-based enforcement is generally minutes, not per request). https://www.moesif.com/docs/api-governance-rules/ , https://www.moesif.com/docs/api-governance-rules/creating-governance-rules/
- Billing meters: they can `sum` any field (e.g. `response.body…usage.completion_tokens`, or metadata) per subscription and sync to Stripe, Chargebee, Zuora and others. They're useful for chargeback, not for warnings. https://www.moesif.com/blog/technical/api-development/Monetizing-AI-APIs-with-Billing-Meters-in-Moesif/
- Dynamic sampling exists. **Budget events must be excluded from sampling** so the once-per-period marker is never dropped. https://moesif.com/docs/platform/dynamic-sampling

## 4. AI/LLM cost features (2024–2026)

- AI cost monitoring guidance (Nov 2024): per-customer cost breakdowns, dashboards, and "alert triggers … when a customer's usage exceeds predefined thresholds". https://www.moesif.com/blog/monitoring/Monitoring-Cost-and-Consumption-of-AI-APIs-and-Apps/
- MCP server observability and metering (2025). https://www.moesif.com/blog/monitoring/model-context-protocol/How-to-Setup-Observability-For-Your-MCP-Server-with-Moesif/
- WSO2 monetization page: LLM token and MCP tool-call metering, multi-model cost attribution (OpenAI, Gemini, Claude, Azure OpenAI, Mistral, Bedrock), "one-click alerting and anomaly detection". https://wso2.com/api-platform/monetization/
- No dedicated "AI budget" or "budget threshold" product feature was found in Moesif as of 2026. Budget logic has to be expressed as metadata plus generic alerts.

## 5. Limits

- Event size: **1 MB hard limit per event**, metadata included. https://moesif.com/docs/ingest-action-events
- Metadata: any JSON object. No published limit on key count or depth (**UNVERIFIED**).
- Ingestion latency: no published SLA. Real-time alerts evaluate every minute, so expect about 1–2 minutes plus the SDK batching interval (**UNVERIFIED**).
- Alert-rule count per plan: not published (**UNVERIFIED**).
- Retention: 7 days on free, 1 year on paid plans. https://moesif.com/price , https://elements.heroku.com/addons/moesif

## Verdict

**Moesif alone can deliver the warnings only if the gateway does the budget arithmetic.** Moesif's alerting can't evaluate "month-to-date spend ≥ X% of budget" mid-period: calendar-month alerts fire only after the month ends, rolling windows cover hours at most, and thresholds are one static number per rule. It can reliably alert, in about a minute, on a **per-event marker** that the gateway sets: a static rule (count ≥ 1, or `any`) over a 15-minute or 1-hour rolling window, filtered on the marker and grouped by budget id. Routing to email, Slack, PagerDuty or webhook and throttling come built in. Behavioral Emails can cover end-customer notices.

## Recommended event shape

Flat scalar metadata keys, because nested arrays are unlikely to group or filter well. One budget per key set; if a request hits several budgets, emit one set per budget with prefixed keys, or one supplementary event per budget.

On **every AI request event** (for dashboards and month-to-date charts):
```
metadata.budget_id            "team-alpha-monthly"
metadata.budget_scope         "team" | "app" | "org"...
metadata.budget_scope_id      "alpha"
metadata.budget_period        "2026-10"
metadata.budget_amount        1000.00     (numeric)
metadata.budget_currency      "USD"
metadata.request_cost         0.0123      (numeric)
metadata.budget_spend         812.45      (spend after this request, numeric)
metadata.budget_percent_used  81.2        (numeric)
```
**Only on the request that first crosses a threshold** (once per budget × period × threshold, deduplicated by the gateway):
```
metadata.budget_threshold_crossed  80        (numeric or string level: 50/80/100)
metadata.budget_alert_key          "team-alpha-monthly:2026-10:80"
```
Moesif setup: one static alert rule per threshold level (or one rule with `any`), filtered on `metadata.budget_threshold_crossed = 80` (or exists), grouped by `metadata.budget_id` (plus `metadata.budget_scope_id` as level 2), window 15 min rolling, threshold count ≥ 1, routed to Slack/email/webhook, throttled. Dashboards: `sum(metadata.request_cost)` or `max(metadata.budget_spend)` by `metadata.budget_id`, monthly buckets, with `max(metadata.budget_amount)` as the budget line.

Caveats: the gateway must make the marker idempotent across replicas and restarts so it fires exactly once. Exclude these events from dynamic sampling. Confirm the alert-rule count limit and ingestion latency with Moesif. Alerting on `budget_percent_used >= 80` directly (as a max over a window) also works but keeps firing on every window until throttled, so the once-only marker is cleaner.
